## 1. Purpose and Scope

This document is the canonical, self-contained record of the forensic investigation into the provenance, raw structure, preprocessing pipeline, and released artifacts of the **Eadro SocialNetwork (SN) dataset**, known in the MUAD paper as **Dataset C**.

**What was investigated:** dataset provenance, raw archive structure, fault-injection ground truth, Eadro's preprocessing pipeline, the MUAD-side data-loading/consumption code, and a recovered snapshot of the actual generated Dataset C chunk artifact.

**Why:** to establish a verified, reproducible basis for regenerating Dataset C from raw data and feeding it into MUAD, without assuming paper prose, repository code, and released data agree with each other.

**What this document represents:** the complete, current state of findings. No prior conversation, note, or earlier report should need to be re-read after this document.

**Explicitly out of scope (deferred to Step 2):** MUAD's model architecture (GPE, CFM, GAT encoders), loss functions, training mathematics, active-learning algorithm internals, and full reproduction of MUAD's training/evaluation procedure beyond the data-pipeline-relevant facts already established below.

## 7. Metrics

### Raw metrics — VERIFIED (direct file inspection)
- Filename structure: `<experiment_dir>/metrics/<service-name>.csv`, one file per service (12 per experiment), consistent naming with Node table in §6.
- CSV header (identical across all inspected files): `timestamp,cpu_usage_system,cpu_usage_total,cpu_usage_user,memory_usage,memory_working_set,rx_bytes,tx_bytes` — **exactly 7 metrics**, matching Eadro's `metric_names` list and order.
- Timestamp format: **absolute Unix epoch, integer seconds**.
- Sampling frequency: **1 row per second** (confirmed: 1412 rows including header for a ~1410s experiment ⇒ 1411 data rows ≈ 1-second cadence).

**The exact 7 metrics:** `cpu_usage_system`, `cpu_usage_total`, `cpu_usage_user`, `memory_usage`, `memory_working_set`, `rx_bytes`, `tx_bytes`.

### Eadro preprocessing — VERIFIED (direct code read, `single_process.py::deal_metrics`)
- Normalization: **z-score** (`(x - mean) / (std + 1e-8)`), computed **per service, per metric, over that service's own single experiment file** (not globally, not per-window, not per-window-per-service).
- Node handling: iterates the 12-node list from `util.py`.
- Windowing: produces `[n_intervals, node_num, chunk_lenth, metric_num]` = `[*, 12, 10, 7]` per experiment, later reshaped per-chunk to `[12, 10, 7]`.

### MUAD artifact — VERIFIED (recovered chunk, §12)
- Tensor shape: `metrics: (12, 10, 7)` — **matches Eadro's own preprocessing output exactly**, no discrepancy for this modality.
- `MetricEncoder` in `models/encoders.py`: `GRUEncoder(in_size=7, out_dim=64)` — **VERIFIED**, matches the 7-metric dimension.

## 8. Logs

### Raw log organization — VERIFIED (direct file inspection of `logs.json`)
- A single JSON object per experiment, keyed by **12 service names** (same names as §6's node table, node 11 keyed as `nginx-web-server` per the alias resolved via Jaeger `processes`, though `logs.json` itself only ever uses service-name keys — the raw log file does not use the `nginx-thrift` alias directly).
- Each value: a flat list of **raw, unparsed log strings**, format: `[YYYY-Mon-DD HH:MM:SS.ffffff] <level>: (file:line:func) message`.
- **Timezone finding — VERIFIED:** log timestamps are in **local time, exactly UTC+8** relative to the Unix-epoch timestamps used everywhere else (metrics CSVs, fault JSONs). Confirmed by direct comparison: first log line `2022-Apr-17 10:12:50.490796` vs. the same experiment's fault-JSON `start` (`1650161565.787468` → UTC `2022-04-17 02:12:45.787468`) — an exact 8-hour offset.
- **UTC+8 conversion requirement — VERIFIED as mandatory, RECONSTRUCTED as an implementation step:** no released code performs this conversion (it isn't needed by Eadro's `single_process.py::deal_logs`, which reads already-converted `logs<idx>.csv`, not raw `logs.json`). Any raw→parsed_data converter must apply this offset explicitly; this was not documented anywhere prior to direct raw-data inspection.

### Log parsing pipeline — VERIFIED (code) / RECONSTRUCTED (raw-to-parsed step)
- Eadro's `single_process.py::deal_logs` (VERIFIED, direct code read) expects **already-parsed** input: `templates.json` (event template list) + `logs<idx>.csv` (rows of timestamp/service/event). It does **not** itself run Drain on raw log strings.
- Drain parsing, HawkesADM4 fitting: **VERIFIED as the documented method** (`tick` library, `HawkesADM4(decay=3)`, per-service-per-window fitting, `baseline_start = ones(event_num)*0.2`), directly read from `single_process.py`. The fitted `model.baseline` vector (length = `event_num`) becomes that service's log feature for the window.
- Actually running Drain on the **raw** `logs.json` strings (with the UTC+8 correction applied first) to produce `templates.json` + `logs<idx>.csv` is a **RECONSTRUCTED** step — no such converter exists in either repository.

### Output tensor / event count — VERIFIED (recovered chunk artifact, §12)
- `logs` tensor shape: `(12, 15)` — i.e., 12 nodes × 15-dimensional Hawkes-intensity vector.
- `event_num: 15` confirmed directly in recovered `metadata.json`.
- MUAD's `LogEncoder`: `nn.Linear(15, out_dim)` — **VERIFIED**, hardcoded to 15, matching this dataset's specific template count (not a universal constant).

## 10. Raw → parsed_data Pipeline

**What raw files exist (VERIFIED, §4–§9):** `SN.fault-*.json` (fault ground truth), `metrics/*.csv` (per-service telemetry), `logs.json` (raw unparsed log strings, keyed by service, local-time UTC+8 timestamps), `spans.json` (raw Jaeger trace/span list with per-trace `processes` map).

**Does an official raw→parsed_data converter exist in the public Eadro repository? NO. VERIFIED.** Confirmed via:
- Full repository commit history (8 commits total; 7 are README edits, 1 is "Add files via upload") — no such script ever existed.
- Repository-wide `grep` for `parsed_data`, `records`, `SN.fault`, `zenodo` finds only *consumption* sites, never a generation script.
- Eadro's own `main.py::run()` calls `load_chunks(data_dir)` unconditionally — it does not orchestrate or fall back to running preprocessing from raw data.

### Original/verified (what the repository actually provides)
- `codes/preprocess/{util,single_process,align}.py` — operate on `parsed_data/`, **not** on the raw Zenodo archive format. Fully verified, see §11.

### Reconstructed (what must be implemented to bridge raw → Eadro's expected input)
All of the following are **RECONSTRUCTED, not original**, and must be labeled as such in any implementation:
1. `metrics/*.csv` → `metrics<idx>/<service>.csv`: near-trivial copy (schema already matches).
2. `logs.json` → `templates.json` + `logs<idx>.csv`: requires (a) UTC+8→UTC timestamp conversion, (b) Drain log-template parsing, (c) reformatting into timestamp/service/event rows.
3. `spans.json` → `traces<idx>.json`: requires resolving `processID`→`serviceName` per-trace (with the `nginx-thrift`/`nginx-web-server` alias applied), converting `startTime`/`duration` from microseconds to the expected per-second-bucket format, and reconstructing `edge_key` from the `references` parent/child relationships.
4. `SN.fault-*.json` → `records<idx>.json`: near-trivial reformatting (`start`→`s`, `end`=`start+duration`, apply the nginx alias to `name`→`service`).

**No code implementing any of the above four steps currently exists in this project or in either official repository.**

## 11. Eadro Preprocessing Implementation

All items below are **VERIFIED by direct reading** of `codes/preprocess/util.py`, `single_process.py`, `align.py`.

- **Node ordering (`util.py`):** fixed 12-node list, exact order and names given in §6's table.
- **Metric processing (`single_process.py::deal_metrics`):** per-service, per-metric z-score normalization over that service's own experiment file; output `[n_intervals, 12, 10, 7]`.
- **Log processing (`single_process.py::deal_logs`):** `event2id` built from `templates.json` (real templates + 1 reserved "Unseen"→id 0); per-service-per-window `HawkesADM4(decay=3)` fit via `tick` library, `baseline_start=ones(event_num)*0.2`; fitted `model.baseline` used as the feature vector.
- **Trace processing (`single_process.py::deal_traces`):** per-node mean latency aggregated into channel 0 of a `[n_intervals, 12, 10, 2]` array; **channel 1 never written by any code path**; channel 0 z-normalized per-node over the whole experiment.
- **Chunk/window length:** `chunk_lenth=10` (default), i.e., **10-second windows**.
- **Stride:** **1 second**, confirmed via `intervals=[(s, s+chunk_lenth-1) for s in range(start, end-chunk_lenth+1)]` in `align.py::get_basic`.
- **Overlap threshold:** default `threshold=1` — a single second of overlap with a fault interval is sufficient to label the entire window anomalous, attributed to that fault's service.
- **Fault labeling / fault-to-node mapping:** `align.py::get_basic` reads `records["faults"]` as `(start,end,service)` triples, maps service name → node id via `info.service2nid`.
- **Normal label:** `-1`, assigned when a window does not overlap any fault interval by the threshold. (Code-level definition; see §12 for the observed absence of `-1` in the one recovered snapshot.)
- **Chunk ID generation (`align.py::get_chunkid()`):** **random 8-character alphanumeric string** (`string.ascii_letters+digits`), with collision checking across the run. **This destroys any encoding of original temporal order or window index in the released chunk format** — confirmed directly from the code; the IDs seen in the recovered chunk pickle (§12) match this scheme exactly (8-char alphanumeric).
- **Shuffle / train-test split behavior (`align.py::split_chunks`):** `np.random.shuffle` over the **flat list of all chunk indices** — split is **at the individual-window level**, with **no grouping by experiment or fault episode**, and **no chronological constraint**.
- **Default test ratio:** CLI argparse default `test_ratio=0.3` (30% test / 70% train). **This does not match the 60/40 split both papers report.**
- **CLI override:** `test_ratio` is overridable at invocation (`--test_ratio 0.4`); the recovered chunk artifact (§12) empirically shows an exact 60.0%/40.0% split, meaning whoever generated it invoked the script with a non-default value.
- **Normalization:** as above — per-service-per-metric (metrics), per-node-per-experiment (traces); **not** global, **not** per-window.
- **Tensor dimensions (as Eadro's own code produces them):** `metrics: [12,10,7]`, `traces: [12,10,2]` (channel 1 always zero), `logs: [12,15]` (event_num dependent on this specific dataset's Drain output), `culprit: int` (`-1` or node id 0–11).
- **Implementation quirks/bugs, documented as-is (no silent fixing):**
  - Trace tensor allocates 2 channels but only ever populates 1 — this is the code's actual behavior, not a hypothesis.
  - `test_ratio` default (0.3) disagrees with both papers' reported split (60/40); the actual released data used a non-default override.
  - Chunk-ID randomization means the released chunk format cannot be audited for temporal/episode-level train-test leakage after the fact, by design of the ID scheme (not necessarily by intent).
